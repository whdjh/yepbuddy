# 12. iPhone 자동 복원과 상태 화면

> 상태: 대기
>
> 선행: [10](10-icloud-settings-backup.md), [11](11-healthkit-record-preservation.md)

## 목표와 범위

같은 Apple 계정의 iPhone 재설치·새 iPhone에서 필요한 건강 접근 권한을 허용하면 운동과 설정을 자동 복원한다. 설정의 백업·복원 메뉴에서는 건강 접근·설정 보존·복원 진행·실패·재시도를 확인할 수 있게 한다.

앱 실행과 기존 권한 흐름에 복원을 연결한다. 별도 로그인·파일 선택·복원 버튼·설정 메뉴 진입을 시작 조건으로 요구하지 않는다. 앱 삭제 경고·첫 기록 저장 후 유실 안내 팝업·삭제 전 백업 바로가기는 추가하지 않는다.

운동·설정의 값뿐 아니라 수정·삭제 의도와 [10번에서 확정한 루틴·위치 상태](./10-icloud-settings-backup.md)를 보존한다. 미확정 항목을 누락한 채 전체 복원을 선언하지 않는다. OS 권한·인증·기기 토큰은 복사하지 않으며 진행 중 네이티브 운동의 삭제·기기 교체 후 재개는 제외한다.

동시 다중 기기 편집은 첫 목표가 아니지만 기존 기기가 다시 연결돼 최신 기록·설정·삭제 결정을 되돌리는 문제는 방지한다. iCloud·HealthKit을 사용할 수 없어도 기존 로컬 운동 기록은 계속 동작해야 한다.

| 상황 | 적용 원칙 |
| --- | --- |
| 유효한 원격 운동·설정 | 임시 영역 검증 후 식별·revision·삭제 계약에 맞춰 로컬 적용 |
| 빈 조회·부분 조회·건강 동기화 지연 | 완전한 원격 목록이나 삭제로 단정하지 않고 로컬 보존·재조회 |
| 복원 중 새 기록·수정·삭제 | 시작 시점의 원격 값으로 덮어쓰지 않고 현재 로컬 변경 유지 |
| 앱 중단·실패·재시도 | 이미 적용한 데이터와 유효한 원본을 유지하고 중복 없이 재개 |
| Apple 계정 전환 | 이전 계정의 대기 쓰기·파일 참조·복원 상태·데이터 출처 분리 |
| 권한·다운로드·미보존 데이터 부족 | 실제 확인 가능한 제한과 재시도 상태를 표시 |

## 작업

- [ ] 앱 시작 시 로컬 데이터·iCloud·건강 접근 상태를 확인하고 접근 목적 설명·필요한 OS 권한 요청을 기존 흐름에 연결한다.
- [ ] 같은 계정의 일반 설정 파일과 옙버디 소유 건강 운동·메타데이터를 조회한다. 소유권·세션 식별자·버전·날짜·수치·메타데이터를 임시 영역에서 검증하고 다른 앱 운동·손상 데이터·미지원 버전을 무리하게 적용하지 않는다.
- [ ] 유효한 운동을 로컬 세션으로 구성하고 건강 샘플·통계에서 심박수·칼로리 요약을 재생성한다. 미수집·미동기화·접근 제한을 고려하고 다른 운동 샘플이나 가짜 값으로 채우지 않는다.
- [ ] 기존 로컬 기록과 식별자로 중복을 제거하고 수정·삭제 충돌 규칙을 적용한다. 복원 중 생성·수정한 기록과 삭제 의도를 유지하고 중단 후에도 안전하게 재개한다.
- [ ] 부분 조회·지연 동기화·구버전 메타데이터와 재시도를 처리한다. 빈 결과로 로컬 기록을 삭제하지 않으며, 계정 전환 시 이전 데이터가 새 계정에 업로드되지 않게 출처·대기 작업을 관리한다.
- [ ] 세션 적용 후 날짜 인덱스·통계와 확정된 루틴/장소 파생 상태를 재구성한다. 건강 운동을 다시 저장하는 완료 처리·과거 캘린더 재등록·완료 알림 재발송을 호출하지 않는다.
- [ ] 현재 기기 권한을 확인해 필요한 예약만 동기화하고 중복 geofence 등록을 막는다. 알림·캘린더 선호값과 실제 OS 허가 상태를 구분한다.
- [ ] [설정 기능서](../page/08_settings.md)에 계획과 현재 구현을 구분해 반영하고 백업·복원 메뉴와 실제 재시도를 구현한다. 건강 접근·HealthKit 로컬 보존·iCloud 설정 보존·전체 복원 상태를 구분한다.
- [ ] 실제 재설치·새 iPhone 복원 결과로 지원 범위를 정리하고 필드별 저장 위치·접근 목적·제한·심사 근거를 개인정보 처리방침과 심사 설명에 반영한다.

## 완료 조건

- [ ] 정상·손상·구버전·미지원·부분 조회·중복·중단 재시도에서 유효한 로컬 기록을 잃지 않고 복원 중 새 기록·수정·삭제를 유지한다.
- [ ] 일반 운동·유산소 구간·일시정지·디로딩·루틴 대체·메모·세트·위치·사용자 설정 fixture를 만들고 대상 값·수정·삭제·누락을 필드별로 비교한다.
- [ ] 같은 iPhone의 실제 앱 삭제 → 재설치 → 건강 접근 허용 후 자동 복원을 확인한다. 설정 메뉴 진입·수동 파일 선택이 필요하지 않다.
- [ ] 같은 Apple 계정의 다른 iPhone에 새로 설치해 기기 전체 백업 복원 없이 같은 흐름을 확인하고, 기존/새 iPhone이 번갈아 연결돼도 중복·역행·삭제 기록 부활이 없다.
- [ ] 기존 버전 기록 전환 후 재설치, 메타데이터 없는 옛 건강 운동, 심박수 없는 기록과 건강/iCloud 지연·미허용·비활성화·오프라인·용량 부족·사용자 데이터 삭제를 확인한다.
- [ ] 복원으로 건강 재저장·과거 캘린더 등록·완료 알림 재발송·중복 geofence 등록·계정 간 업로드가 발생하지 않고 OS 권한을 저장값으로 허용 처리하지 않는다.
- [ ] 설정 화면·기능서·재시도가 실제 상태와 일치한다. 설정 파일 저장 시각·HealthKit 로컬 저장 성공을 전체 운동 백업이나 다른 기기 동기화 완료로 표시하지 않는다.
- [ ] 개발 빌드와 TestFlight/배포 구성에서 HealthKit·iCloud entitlement와 실제 복원·상태 UI를 확인한다. `bunx tsc --noEmit --pretty false`, `bun run lint`와 변경 범위의 native 계약 검사 결과·기기·미검증 항목을 남긴다.
- [ ] 10~11번의 보존·전환 검증과 이번 전체 흐름을 대조하고 지원 항목·미확인 항목·미지원 대안을 구분한다. 전체 완료 조건을 충족했을 때만 복원을 완료로 처리한다.

## 근거와 주의점

- [로컬 저장소](../../src/entities/workout-session/model/storedWorkoutSessionStorage.ts)와 [세션 타입](../../src/entities/workout-session/model/types.ts)을 기준으로 외부 운동에서 세션·날짜 인덱스를 재구성한다.
- [상세 건강 조회 조합](../../src/entities/workout-session/lib/sessionHealthKitData.ts)의 UUID 기반 조회와 별개로, 로컬 목록이 비어 있어도 옙버디가 보존한 건강 운동을 찾을 수 있어야 한다.
- [HealthKit API](../../src/entities/workout-session/api/healthKit.ts)의 저장·조회 경로와 [네이티브 완료 처리](../../plugins/ios/workout-session/LiveWorkoutSessionController.swift)의 완료 후처리를 복원 적용에서 구분한다.

[HealthKit 접근 권한](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data)에 따라 빈 조회만으로 읽기 거부·원격 삭제를 확정하지 않는다. 처음 조회한 결과를 완전한 목록으로 보고 로컬 데이터를 정리하지 않는다.

[건강 앱 개인정보 안내](https://www.apple.com/legal/privacy/data/en/health-app/)와 [iCloud 문서 동기화](https://developer.apple.com/documentation/uikit/synchronizing-documents-in-the-icloud-environment)의 동기화·다운로드 상태를 고려한다. 외부에 보존되지 않은 로컬 데이터와 원본이 사라진 과거 값은 재설치 후 복구를 보장하지 않는다.

[App Review 건강정보 지침](https://developer.apple.com/app-store/review/guidelines/#health-and-health-research)과 [불명확한 CloudKit 저장에 관한 Apple 직원 답변](https://developer.apple.com/forums/thread/838493)을 근거로 실제 저장 위치·제한·미확정 해석을 설명한다. API가 있다는 사실이나 암호화·사용자 동의만으로 허용을 단정하지 않는다.

정적 계약 검사·시뮬레이터 결과·앱 실행 성공은 실제 재설치 복원·동기화·심사 통과 증거가 아니다. 건강 권한을 다시 허용해야 할 수 있다는 조건과 필드별 미지원·미검증 범위를 실제 사용자 설명에도 반영한다.
