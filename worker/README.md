# YepBuddy Worker

쿠팡 파트너스 상품 가격을 주기적으로 확인해 Supabase에 일별 이력으로 저장하고, 모바일 앱의 가격대 판정과 가격 추이 그래프로 연결하는 워커입니다.

현재 코드는 기존 `protein_prices_daily`를 사용합니다. 모바일 앱은 `yb_` 테이블과 RPC로 전환했으며, 아래 기존 구현을 새 앱용 수집기로 전환하는 작업은 아직 완료하지 않았습니다.

## 핵심 구현

### 가격 이력을 구매 판단 정보로 전환한 프로틴 가격 추적

> 상품별 가격을 일별 이력으로 축적하고 현재가를 해당 상품의 과거 가격과 비교해 상대적인 가격 수준을 제공합니다.

#### 문제

현재 가격만으로는 평소보다 저렴한지 판단하기 어렵고, 상품마다 가격대가 달라 하나의 고정 금액을 공통 기준으로 사용할 수도 없었습니다.

#### 핵심 선택

GitHub Actions로 가격 조회를 30분 간격으로 예약하고, 검색 결과에서는 미리 지정한 상품과 일치하는 값만 선택했습니다. 현재 가격은 자주 갱신하되 가격 이력은 일 단위로 유지하기 위해 같은 날짜의 데이터는 새로운 행을 추가하지 않고 최신 값으로 갱신했습니다.

```js
await supabase
  .from("protein_prices_daily")
  .upsert([insertData], {
    onConflict: "protein_id,observed_date",
    ignoreDuplicates: false,
  })
```

워커는 가격을 수집하고 저장하는 역할만 담당합니다. 모바일 앱은 조회한 가격 통계로 현재 가격대를 판정합니다. 표본이 충분하면 과거 가격의 하위 20%와 상위 20% 경계값을 사용하고, 표본이 부족하면 중앙 가격 대비 10% 범위를 임시 기준으로 사용합니다.

```ts
if (
  p20 != null &&
  p50 != null &&
  p80 != null &&
  Number.isFinite(p20) &&
  Number.isFinite(p50) &&
  Number.isFinite(p80) &&
  sampleCount >= 5
) {
  if (price <= p20) return { kind: "low", color: "green", reason: "P20 이하" }
  if (price >= p80) return { kind: "high", color: "red", reason: "P80 이상" }
  return { kind: "mid", color: "blue", reason: "중간 구간" }
}

if (p50 != null && Number.isFinite(p50) && p50 > 0) {
  if (price <= p50 * 0.9) {
    return { kind: "low", color: "green", reason: "중앙값-10% 이하" }
  }
  if (price >= p50 * 1.1) {
    return { kind: "high", color: "red", reason: "중앙값+10% 이상" }
  }
  return { kind: "mid", color: "blue", reason: "중앙값±10%" }
}
```

목록에서는 저점, 중간, 고점 배지로 현재 가격 수준을 빠르게 비교하고, 상세 화면에서는 조회된 가격 이력의 최고가와 최저가 및 추이 그래프로 가격 변화의 맥락을 제공합니다.

#### 결과

- 30분 간격으로 현재 가격을 확인하고 상품별 일별 가격 이력 축적
- 같은 날짜의 중복 행 없이 현재 가격을 최신 값으로 갱신
- 상품별 과거 가격을 기준으로 상대적인 가격대 제공
- 목록 배지와 상세 가격 추이 그래프로 구매 판단 지원

#### 현재 한계

- 가격대 기준은 사용자 행동으로 검증된 절대 기준이 아닌 초기 제품 가설
- 같은 날의 중간 가격은 덮어쓰므로 일중 가격 변화는 보존하지 않음
- 차트는 관측 순서를 사용하므로 누락된 날짜 사이의 실제 시간 간격을 표현하지 않음

## 보충제 수집기 전환 — 미구현

2026-10-11 기준 쿠팡 API는 미발급이며, 새 수집기 실행·예약은 시작하지 않았다. API 발급 후 아래 규칙으로 구현한다. 커밋은 사용자가 진행한다.

### 현재 DB와 과거 가격

현재 연결된 기존 공용 DB에 `yb_supplements`, `yb_supplement_prices_daily`, `yb_supplement_topic`과 읽기 RPC 2개를 적용했다. 다른 서비스의 DB 객체는 변경하지 않는다.

- 앱 계약: [프로틴 기능서](../mobile/docs/page/10_protein.md), [Entities 가이드](../mobile/src/entities/README.md).
- RLS 활성화, 앱 역할은 읽기 전용. `service_role`은 제품 읽기와 가격 읽기·INSERT·UPDATE가 가능하고 제품 쓰기·가격 DELETE는 불가하다.

채찍단 페이지 호스트는 `https://www.cowlr.kr`이다. 가격은 공개 그래프 API `https://api.cowlr.kr/product/price/{source_id}/daily?period=1y`에서 확보했다.

- 백필 구간은 KST `2026-01-01`~`2026-10-10` 양끝 포함. 원본 `date`의 Unix 밀리초를 `Asia/Seoul` 날짜로 변환하고 `min_price`만 KRW 정수로 저장했다.
- 총 2,189행이며 각 제품의 첫·마지막 기록은 구간 양끝과 같다. 원본에 없는 제품·날짜 조합 75개는 채우지 않았고 날짜별 같은 가격은 유지했다.
- 백필의 `min_price_first_observed_at`, `url`은 모두 `NULL`. `max_price`, `latest_price`, `latest_date`로 가격·시각·URL을 추정하지 않는다. `source` 컬럼도 추가하지 않는다.
- 원본과 DB의 전체 행 대조, 공개 키의 최신 가격·전체 이력 RPC 조회와 날짜·가격 일치를 검증했다. 일회성 등록·백필 자료는 정리했다.
- ID 1~8의 설명은 빈 문자열, 맛 평가는 빈 배열이다. 설명은 사용자가 제공해야 한다.
- ID 10·11에는 설명 `가성비, 월과 일이 같을때 세일, 공휴일에 가끔 세일`과 동일한 맛 평가 31개(T1 6개·T2 11개·T3 14개)를 저장했다. 가격 수집·표시에서 제외하며 구매 URL은 [purchaseLinks.ts](../mobile/src/entities/protein/model/purchaseLinks.ts)에 있다.

### 구현할 수집 규칙

- 대상 ID 1~8을 Worker의 고정 `{ supplementId, keyword }` 배열로 관리한다. DB에 추적 플래그를 추가하지 않고 검색어를 제품 필드로 자동 조합하지 않는다.
- 제품·맛·용량이 모두 일치하는 SKU만 인정한다. 판매자는 달라도 되지만 여러 통·세트는 제외한다. 묶음 가격 환산과 추정 할인율을 적용하지 않는다.
- 날짜는 `Asia/Seoul`, 유일 키는 `(supplement_id, observed_date)`다. 오늘 행이 없으면 삽입하고 더 낮은 가격일 때만 가격·최초 관측 시각·URL을 원자적으로 함께 갱신한다. 같거나 높은 가격은 모든 값을 유지한다.
- 최초 관측 시각은 수집기가 그날의 최저가를 처음 발견한 시각이다. 실제 쿠팡 가격 변경 시각으로 해석하지 않는다.
- Search에서 유효 후보의 최저가를 선택해 오늘 DB 가격과 비교한다. 새 행이거나 더 싼 경우에만 Deeplink를 호출하여 파트너스 URL과 함께 저장한다. Deeplink 실패 시 처리 방식은 구현 전에 결정한다.
- 목표 예약은 약 5분 간격, concurrency 그룹은 `supplement-price-crawler`, `cancel-in-progress: false`다. 기존 30분 Workflow에는 아직 적용하지 않았다.
- 실행당 최대 45회 요청 시도, 호출 사이 최소 1,500ms를 적용한다. Search·Deeplink와 실패한 요청도 시도 전에 횟수를 증가시키며 46번째 요청은 보내지 않는다. 이는 자체 안전값이며 공식 제한의 시간·계정 범위는 따로 확인해야 한다.
- API 실패나 호출 한도 도달 시 즉시 재시도하지 않는다. 처리하지 못한 현재 제품의 cursor를 저장하고 종료한 뒤 다음 예약 실행에서 해당 제품부터 원형 순회한다.
- Cursor는 `targets`의 0부터 시작하는 index다. 대상 순서를 고정하고 새 제품은 뒤에 추가한다. DB가 아닌 GitHub Actions 쪽에 실행 간 영구 저장하며, 환경변수 선언만으로 값이 유지된다고 가정하지 않는다. 구체적인 저장 수단은 미정이다.

### 재개 순서와 남은 확인

1. API 발급과 실제 호출 제한을 확인하고 SKU별 검색어·가격 필드·필터, 후보 없음·Deeplink 실패·DB 실패·cursor 저장 실패 시 처리와 cursor 영구 저장 수단을 정한다.
2. 제품 하나로 검색부터 일일 최저가 저장까지 검증한 뒤 8개 원형 순회와 예약으로 확대한다. 낮은 가격의 동시 갱신, 동일·높은 가격의 값 보존, KST 자정, SKU 판별, 46번째 호출 차단, 실패 후 재개를 확인한다.
3. 기존 [Workflow](../.github/workflows/crawl-coupang.yml), tracker 및 외부 예약의 활성 여부·중복 호출을 확인한다. 기존 코드는 UTC 날짜·최종값 upsert·일부 묶음 환산을 사용하므로 새 규칙에 그대로 재사용하지 않는다. 마이프로틴 세일 알림은 별도 기능이다.
4. 직접 수집 시작일을 기록하고 `2026-10-11`부터 시작 전날까지 확보 가능한 원본만 추가 백필한다. 누락 날짜를 만들지 않고 기존 가격을 덮어쓰지 않는다.
5. 앱의 iOS/Android 화면·테마·접근성·구매 링크와 배포를 확인한다. 실기기와 배포는 아직 미확인이다.
6. 구버전 앱의 기존 테이블·RPC 의존성과 복구 방법을 확인한 뒤 기존 수집기·DB 객체 정리를 별도 진행한다. 현재 파일 정리는 DB 삭제나 프로젝트 설정 변경의 승인이 아니다.
